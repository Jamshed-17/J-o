#projects 
## 🎯 1. Общие требования к проекту

- **Целевая платформа:** Веб-приложение (Single Page Application, SPA).
    
- **Хост API:** `https://atomgrad.site` (порт 80/443 через прокси, порты **8000** и **5432** не должны использоваться напрямую).
    
- **Базовый URL API:** `https://atomgrad.site/` (или `/api/`, если используется проксирование на сервере).
    
- **Язык:** Русский.
    
- **Аутентификация:** Использование JWT-токенов, передаваемых через HTTP-only Cookie.
    
- **Структура:** Приложение должно иметь две основные части: **Публичную** (для всех пользователей) и **Административную** (защищенную).

## 🧩 2. Публичный раздел (Главная страница)

Основная цель: отображение информации о персонах.

|**#**|**Элемент**|**Описание**|**Метод API**|**Эндпоинт**|**Требования**|
|---|---|---|---|---|---|
|2.1|**Список Персон**|Отображение превью всех персон.|`GET`|`/persons/all`|Выводит список всех персон с полями `name`, `about`, `text`, `photo`, `sourses`, `autor`.|
|2.2|**Поиск по имени**|Возможность найти ID персоны по полному имени.|`GET`|`/persons/{name}`|Необходим для быстрого перехода на страницу, если прямого поиска по ID нет.|
|2.3|**Страница Персоны**|Детальное отображение информации по ID.|`GET`|`/persons/id/{person_id}`|Выводит полную информацию (включая **text** и **sourses**, которые являются массивами).|
|2.4|**Статика**|Отображение фотографий.|`GET`|`/static/{filename}`|Фотографии доступны через `/static/`. Фронтенд должен корректно обрабатывать путь `photo` из API.|

## 🔒 3. Административный раздел (CRUD)

Доступ к этому разделу возможен только после успешной аутентификации. Все запросы к `/admin` должны содержать действительный Cookie `access_token`.

### 3.1. Аутентификация

|**#**|**Элемент**|**Описание**|**Метод API**|**Эндпоинт**|**Требования**|
|---|---|---|---|---|---|
|3.1.1|**Вход (Login)**|Форма для ввода логина и пароля.|`POST`|`/auth/login`|**Payload:** `{login: str, password: str}`. При успехе устанавливается **HTTP-only Cookie** `access_token` и возвращается `{message: "Logged in"}`.|

### 3.2. Управление персонами

Вся работа ведется через роутер `/admin/persons`.

|**#**|**Элемент**|**Описание**|**Метод API**|**Эндпоинт**|**Требования**|
|---|---|---|---|---|---|
|3.2.1|**Создание**|Форма для добавления новой персоны.|`POST`|`/admin/persons/`|**Payload:** `schemas.PersonCreate`.|
|3.2.2|**Изменение**|Форма для редактирования существующей персоны по ID.|`PUT`|`/admin/persons/{person_id}`|**Payload:** `schemas.PersonCreate`.|
|3.2.3|**Удаление**|Кнопка удаления персоны по ID.|`DELETE`|`/admin/persons/{person_id}`|Не требует тела запроса.|

## 🔑 4. Специфика и обработка данных

- **CSRF/CORS:** Бэкенд настроен для обработки CORS. Поскольку используется Cookie с флагом `httponly`, фронтенд должен быть внимателен к защите от CSRF-атак.
    
- **Массивы (JSONB):** Поля `text` (биография) и `sourses` (источники) приходят и отправляются в виде **массива строк** (`List[str]`). Фронтенд должен предоставить удобный интерфейс для ввода и отображения этих данных (например, поле с разделителями или динамические списки ввода).
    
- **Обработка ошибок:**
    
    - При ошибках 401 (Неавторизован, неверный токен) или 403 (Нет прав) фронтенд должен перенаправлять пользователя на страницу входа (`/login`).
        
    - При 404/422/500 должен отображаться соответствующий текст ошибки.
        
- **Инициализация:** При первом запуске (первом `docker compose up`) бэкенд автоматически создает:
    
    - Базу данных.
        
    - Супер-администратора (из `.env`).
        
    - Данные (сидинг) из файлов JSON.

## 🔗 5. Рекомендации по интеграции

- **API Client:** Рекомендуется создать централизованный класс или модуль для работы с API (например, `ApiClient.js`), который будет обрабатывать ошибки аутентификации (401) и автоматически перенаправлять пользователя.
    
- **Токен:** Токен не передается напрямую. После успешного входа, браузер автоматически прикрепляет Cookie `access_token` ко всем запросам к API. Не нужно вручную добавлять заголовок `Authorization`.
